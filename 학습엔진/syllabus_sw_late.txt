순환 :: A가 B를 부르고 B가 다시 A를 부르는 순환 의존(Cyclic Dependency)이 왜 독립적인 이해와 테스트, 배포를 불가능하게 만드는지 확인한다.

인터페이스로 :: 상위 정책이 하위 세부 구현에 끌려다니지 않도록, 상위 모듈이 필요한 인터페이스를 정의하고 하위 모듈이 이를 구현하게 한다(DIP).
하위가 상위를 :: 유틸리티나 인프라 모듈이 도메인 상위 모듈을 역으로 참조할 때 생기는 계층 오염을 찾아 바로잡는다.
방향 그림 :: 리팩터링 전후의 의존성 그래프를 비교해 화살표가 한 방향(비순환 방향 그래프)으로 정리되었는지 확인한다.
빌드 의존 :: 논리적 설계 경계와 실제 물리적 패키지·모듈 경계가 일치하는지 점검한다.
테스트 의존 :: 테스트하기 어렵다는 신호가 곧 의존성 방향이 꼬여 있다는 설계 신호임을 사례로 확인한다.
데이터 의존 :: 외부 API 응답 DTO나 DB 엔티티 구조가 핵심 도메인 로직 끝까지 그대로 침투했을 때 생기는 취약성을 분석하고 변환 경계(Anti-Corruption Layer)를 둔다.
한 방향 :: 변경되기 쉬운 모듈이 안정된 핵심 모듈에 의존하게 만들고, 그 반대 방향은 허용하지 않는(Stable Dependencies Principle) 이유를 정리한다.
예외적 역방향 :: 성능이나 단순성을 위해 계층을 건너뛰는 지름길을 허용할 때, 그 범위를 어디까지로 제한할지 기준을 적는다.
그림 갱신 :: 새로운 기능을 추가할 때 가장 먼저 의존성 화살표가 어디로 향할지 스케치하는 습관을 들인다.
방향 점검 :: 얽혀 있는 모듈 구조 하나를 골라 순환을 끊고 도메인 정책이 중심에 오도록 의존성 방향을 재설계한다.

모델 오염 방지 :: 외부 레거시 시스템의 기형적인 데이터 구조가 우리 도메인 모델 안으로 들어오지 못하도록 번역 계층을 설계한다.
모델 비교 :: 같은 업무 규칙을 '객체지향 풍부한 모델'과 '불변 데이터 + 순수 함수 파이프라인' 두 방식으로 설계해 장단점을 대조한다.
모델 점검 :: 문제의 복잡도에 따라 단순 데이터 구조, 트랜잭션 스크립트, 풍부한 도메인 모델, 읽기·쓰기 분리 중 무엇을 택할지 판단 기준을 백지에 정리한다.
동기 호출과 비동기 흐름의 설계|287|299|모델|흐름|즉시 응답을 받는 동기(Synchronous) 설계와 큐·메시지를 거치는 비동기(Asynchronous) 설계의 지연 시간, 결합도, 복잡도 트레이드오프를 다룬다.
동기 흐름 :: 요청과 응답이 한 호출 스택 안에서 끝나는 동기 방식의 직관성과, 하위 시스템 하나가 느려질 때 전체가 멈추는 시간적 결합을 분석한다.
비동기 분리 :: 무거운 작업이나 외부 연동을 큐 뒤로 분리했을 때 얻는 응답성·완충 효과와, 그 대가로 생기는 '지금 처리 중' 상태 관리 비용을 비교한다.
메시지 전달 보장 :: 네트워크 너머에서는 '정확히 한 번(Exactly-once)' 전달이 왜 환상에 가까운지 이해하고, '최소 한 번(At-least-once) 전달 + 멱등한 처리'로 설계하는 원리를 익힌다.
멱등성 설계 :: 같은 요청이나 메시지가 두 번 들어와도 결과 상태가 한 번 처리한 것과 같아지도록 멱등 키(Idempotency Key)와 상태 검사를 설계한다.
배압과 흐름 제어 :: 생산자가 소비자보다 빠르게 작업을 밀어 넣을 때 큐가 폭발하지 않도록 배압(Backpressure)과 제한(Rate Limit)을 두는 법을 배운다.
순서 역전 :: 비동기·병렬 처리에서는 먼저 보낸 이벤트가 나중에 도착할 수 있음을 전제하고, 버전 번호나 타임스탬프로 역전을 방어한다.
사가와 오케스트레이션 :: 여러 단계의 분산 작업을 중앙 조정자(Orchestration)가 지휘할 때의 명확함과, 이벤트로 서로 반응(Choreography)할 때의 느슨함을 비교한다.
부분 실패 :: 작업의 일부만 성공하고 일부는 실패한 어중간한 상태를 사용자와 운영자에게 어떻게 드러내고 복구할지 설계한다.
폴링과 푸시 :: 상태 변화를 주기적으로 물어보는 폴링(Polling)의 단순함과, 변경 즉시 밀어 주는 푸시(Webhook, 스트림)의 실시간성·연결 관리 비용을 비교한다.
배치와 스트림 :: 데이터를 모아 주기적으로 처리하는 배치(Batch) 설계와, 사건이 발생할 때마다 즉시 흘려보내는 스트림 설계의 득실을 따진다.
동기처럼 보이는 비동기 :: 내부는 비동기로 처리하더라도 사용자 경험이 깨지지 않게 상태 전이를 명확히 설계한다.
흐름 비교 노트 :: 한 업무 흐름을 동기 직렬 호출로 짰을 때와 비동기 큐 기반으로 짰을 때의 장애 전파 범위와 디버깅 난이도를 비교한다.
흐름 점검 :: 지연 시간, 처리량, 일관성 요구사항이 주어졌을 때 어디를 동기로 묶고 어디를 비동기로 끊을지 경계를 설계한다.
가변 상태와 동시성 설계|300|312|흐름|동시성|공유 가변 상태(Shared Mutable State)를 잠금으로 지키는 방식과, 불변 데이터·메시지 전달로 공유 자체를 없애는 방식을 대조한다.
공유 가변의 위험 :: 두 실행 흐름이 같은 상태를 동시에 읽고 쓸 때 발생하는 경쟁 조건(Race Condition)과 잃어버린 갱신(Lost Update)을 손으로 추적한다.
비관적 잠금 :: 충돌이 잦을 때 미리 자원을 잠그는 비관적 잠금(Pessimistic Lock)의 안전성과, 처리량 저하·교착 상태 위험을 분석한다.
낙관적 동시성 :: 잠그지 않고 읽은 뒤, 쓸 때 버전 번호가 그대로인지 확인하는 낙관적 동시성 제어(OCC, CAS)가 언제 유리한지 비교한다.
교착 상태 :: 두 흐름이 서로 상대방이 가진 자원을 기다리며 영원히 멈추는 교착 상태(Deadlock)의 조건과, 잠금 순서를 고정해 이를 예방하는 원칙을 배운다.
불변성 :: 상태를 제자리에서 고치는 대신 새 값을 만들어 반환하는 불변(Immutability) 설계가 어떻게 동시성 추론을 극적으로 단순하게 만드는지 확인한다.
상태 격리 :: 상태를 여러 스레드가 공유하는 대신, 한 주체(Actor, 단일 스레드 루프)만 그 상태를 소유하고 메시지로만 요청을 받는 모델을 비교한다.
원자적 연산 :: '확인 후 행동(Check-Then-Act)' 두 단계가 쪼개질 때 생기는 빈틈을 찾고, 이를 하나의 원자적 연산으로 합치는 법을 익힌다.
캐시와 원본의 불일치 :: 읽기 속도를 위해 둔 캐시가 원본 데이터와 어긋날 때(Cache Invalidation), 짧은 불일치를 허용할지 무효화 경로를 어떻게 둘지 설계한다.
메모리 가시성 :: 한 흐름이 바꾼 값이 다른 흐름에 즉시 보이지 않을 수 있다는 가시성·순서 재배치 문제를 고수준 동기화 도구로 다루는 이유를 이해한다.
부작용 격리 :: 순수하게 계산만 하는 코어(Functional Core)와 외부 상태·동시성을 다루는 껍데기(Imperative Shell)를 분리해 테스트와 추론을 쉽게 만든다.
동시성 재현 :: 타이밍에 따라 가끔만 터지는 동시성 버그를 결정론적으로 재현하고 검증하기 위한 설계 구조를 궁리한다.
동시성 비교 :: 같은 카운터·재고 차감 문제를 비관적 잠금, 낙관적 버전 비교, 단일 큐 직렬화 세 방식으로 설계해 장단점을 표로 정리한다.
동시성 점검 :: 공유 가변 상태를 어디까지 불변으로 바꿀 수 있는지, 꼭 공유해야 하는 지점에는 어떤 동시성 제어를 둘지 설계안을 작성한다.
실패를 전제한 복원력 설계|313|325|동시성|복원력|모든 의존성이 언제든 느려지거나 죽을 수 있다고 가정하고, 작은 부분의 실패가 전체 시스템 장애로 번지지 않게 막는 격리 설계를 익힌다.
단일 장애점 :: 그 구성요소 하나만 멈춰도 전체가 멈추는 단일 장애점(SPOF)을 아키텍처 그림에서 찾아내는 법을 배운다.
타임아웃 :: 외부 호출에 타임아웃이 없을 때 왜 스레드와 자원이 고갈되어 연쇄 장애가 일어나는지 분석하고, 적절한 제한 시간을 두는 원칙을 세운다.
무한 재시도의 독 :: 장애가 난 하위 시스템에 모든 호출자가 즉시 재시도를 퍼부을 때(Retry Storm) 오히려 복구를 막는 현상을 분석하고 지수 백오프·지터를 적용한다.
서킷 브레이커 :: 실패가 반복되는 경로를 아예 빠르게 차단(Fail-Fast)해 자원을 보호하고 하위 시스템이 회복할 시간을 주는 차단기 패턴을 이해한다.
벌크헤드 격리 :: 배의 격벽처럼 자원 풀이나 큐를 용도별로 분리해, 한 기능의 폭주가 다른 핵심 기능까지 침몰시키지 않게 격리한다.
우아한 성능 저하 :: 추천이나 부가 통계 기능이 죽더라도 핵심 결제·조회 기능은 기본값으로라도 계속 동작하게 하는 우아한 저하(Graceful Degradation)를 설계한다.
폴백의 위험 :: 장애 시 타는 대체 경로(Fallback)가 평소에는 테스트되지 않다가 정작 장애 순간에 또 다른 장애를 일으키는 함정을 경계한다.
용량 한계와 버리기 :: 시스템이 감당할 수 있는 한계를 넘는 요청이 몰릴 때, 모두 함께 느려져 죽는 대신 일부 요청을 앞에서 빠르게 거절(Load Shedding)하는 판단을 배운다.
관측 가능성 :: 장애가 났을 때 추측하지 않고 원인을 찾으려면 설계 단계부터 어떤 지표(지연 시간, 오류율, 포화도)와 맥락 로그가 심어져 있어야 하는지 정리한다.
의존성 등급 :: 외부 의존성을 '없으면 서비스 불가(Tier 1)'와 '없어도 축소 운영 가능(Tier 2)'으로 나누어 결합 방식을 다르게 가져간다.
복구 우선 설계 :: 평균 무고장 시간(MTBF)만 늘리려는 설계와, 고장이 나도 평균 복구 시간(MTTR)을 짧게 만드는 설계의 차이를 비교한다.
장애 주입 사고 실험 :: 아키텍처의 화살표 하나를 지우거나 지연을 10초로 늘렸을 때 시스템이 어떻게 반응하는지 종이 위에서 추적(Chaos tabletop)한다.
복원력 점검 :: 외부 연동이 포함된 설계 하나를 골라 타임아웃, 재시도 한계, 격벽, 축소 운영 경로를 빠짐없이 갖춘 복원력 설계를 완성한다.
선행 설계 vs 진화적 아키텍처|326|338|복원력|진화|처음부터 완벽한 구조를 짜려는 선행 설계(BDUF)와 아무 계획 없이 임기응변만 쌓는 극단을 모두 피하고, 변화에 맞춰 안전하게 진화하는 설계를 익힌다.
되돌리기 어려운 결정 :: 한 번 정하면 바꾸기 비싼 결정(외부 공개 API, 핵심 데이터 스키마, 모듈 경계)과 언제든 쉽게 바꿀 수 있는 내부 구현을 구분한다.
선행 설계의 함정 :: 아직 겪어 보지 않은 미래의 요구사항을 상상해 거대한 확장 프레임워크(YAGNI 위반)를 미리 만들었을 때 생기는 유지보수 빚을 분석한다.
전술적 함정 :: 반대로 아우스터하우트가 경고한 '전술적 토네이도'처럼, 당장 돌아가게만 짜고 구조를 전혀 돌보지 않을 때 복잡도가 어떻게 폭발하는지 대조한다.
전략적 투자 :: 전체 작업 시간의 10~20%를 꾸준히 인터페이스 정리와 복잡도 제거에 투자하는 전략적 프로그래밍이 장기 속도를 어떻게 역전시키는지 본다.
확장 후 축소 :: 이미 쓰이고 있는 인터페이스나 스키마를 바꿀 때, 새 구조를 먼저 나란히 추가(Expand)하고 호출자를 옮긴 뒤 옛 구조를 지우는(Contract) 무중단 진화 기법을 익힌다.
스트랭글러 피그 :: 낡고 거대한 레거시 모듈을 한 번에 다 새로 짜서 바꾸려다 실패하는 대신, 가장자리 기능부터 하나씩 새 모듈로 감싸 대체하는(Strangler Fig) 전략을 배운다.
추상화로 가지치기 :: 내부의 낡은 구현을 당장 다 고칠 수 없을 때, 그 앞에 깨끗한 추상화 계층(Branch by Abstraction)을 먼저 세워 오염 확산을 막는다.
기술 부채의 이자 :: 설계 타협을 했을 때 막연하게 '나중에 고치자'고 두지 않고, 그 타협 때문에 매번 추가로 치르고 있는 구체적인 변경 비용(이자)을 측정한다.
적합도 함수 :: 아키텍처가 지켜야 할 핵심 속성(의존 방향, 응답 시간, 결합도 한계)을 자동화된 검사(Fitness Function)로 두어 퇴행을 막는다.
더 단순한 설계로 :: 요구사항이 줄어들거나 가정이 틀렸음이 밝혀졌을 때, 복잡해진 아키텍처를 과감히 더 단순한 구조로 축소(Downscale)하는 판단을 연습한다.
버전 공존 :: 외부 호출자를 위해 구버전과 신버전 인터페이스를 동시에 지원하는 기간과 어댑터 구조를 설계한다.
진화 시나리오 :: 처음에는 단일 모듈로 시작해 트래픽과 팀 규모가 커짐에 따라 세 단계로 구조를 진화시키는 로드맵을 그려 본다.
진화 점검 :: '지금 당장 필요한 단순함'과 '나중에 길을 막지 않는 경계'를 동시에 만족하는 진화적 설계안을 작성한다.
설계 카타와 다관점 비평|339|351|진화|종합|다양한 도메인 문제를 놓고 서로 상반된 설계 거장들의 시각으로 교차 비평하며, 어떤 문제 앞에서도 스스로 설계 대안을 도출하는 훈련을 한다.
카타 1 알림 시스템 :: 다채널 알림 발송 시스템을 '확장성 중심(플러그인·이벤트)'과 '단순성·추적성 중심(직접 파이프라인)' 두 가지로 설계해 비교한다.
카타 2 요금과 할인 :: 복잡한 중첩 할인 규칙을 '객체지향 데코레이터·합성 패턴'과 '불변 규칙 데이터 + 순수 계산 함수'로 각각 설계해 대조한다.
카타 3 예약과 좌석 :: 동시 요청이 몰리는 좌석 예약을 'DB 비관적 잠금 중심'과 '메모리 직렬화·비동기 확정 중심'으로 각각 설계해 비교한다.
카타 4 외부 연동 :: 불안정한 외부 결제·배송 연동을 다루는 경계를 설계하고, 정상 흐름 코드와 오류·재시도·격리 코드가 섞이지 않게 분리한다.
카타 5 파일과 스트림 :: 대용량 데이터를 처리할 때 전체를 메모리에 올려 변환하는 직관적 구조와, 청크·스트림으로 흘려보내는 구조의 경계를 설계한다.
마틴의 시선 :: 위 설계들 중 하나를 로버트 마틴(Clean Code, SOLID)의 관점에서 읽고, 함수 크기·책임 분리·의존성 역전이 잘 되었는지 비평한다.
아우스터하우트의 시선 :: 똑같은 설계를 존 아우스터하우트(A Philosophy of Software Design)의 관점에서 다시 읽고, 얕은 모듈·정보 누수·과도한 분할이 없는지 반론을 쓴다.
파울러와 벡의 시선 :: 마틴 파울러와 켄트 벡의 관점에서, 현재 설계가 다음 변경을 위해 먼저 정돈(Tidy)하기 쉬운 구조인지 평가한다.
클레프만의 시선 :: 마틴 클레프만(DDIA)의 관점에서, 부분 실패·동시성·데이터 일관성이 깨질 때 이 설계가 어떻게 버티는지 점검한다.
관점 충돌 해결 :: 네 관점이 서로 다른 답을 가리킬 때, 현재 시스템의 가장 큰 고통(변경 빈도, 장애 비용, 팀 숙련도)을 기준으로 우선순위를 매긴다.
나만의 설계 기준표 :: 문제를 만났을 때 던질 핵심 질문 열 가지(무엇이 변하는가, 무엇을 숨길 것인가, 실패하면 어떻게 되는가 등)를 한 장의 체크리스트로 만든다.
설계 구술 설명 :: 화이트보드나 빈 종이만 놓고 10분 안에 문제, 대안 둘, 선택한 구조, 감수한 단점을 막힘없이 설명하는 연습을 한다.
종합 점검 :: 처음 보는 요구사항 하나를 받아 40분 안에 두 가지 상반된 설계안을 도출하고 트레이드오프 근거까지 완성한다.
아키텍처 의사결정 기록과 설계 핸드북|352|364|종합|기록|7년 동안 체화한 소프트웨어 설계 원리와 상반된 관점의 판단 기준을 언제든 꺼내 쓸 수 있는 아키텍처 의사결정 기록(ADR)과 개인 설계 핸드북으로 집대성한다.
목표 문장 :: 내가 지향하는 좋은 소프트웨어 설계란 무엇인지(복잡도 통제, 변경 용이성, 명확한 경계)를 한 문단의 설계 철학으로 정의한다.
과업 범위 :: 설계로 해결할 수 있는 문제와 설계만으로 해결할 수 없는 문제를 구분하고, 과잉 설계를 경계하는 기준을 적는다.
복잡도 요약 :: 복잡도를 알아차리는 세 가지 신호와, 복잡도를 모듈 안으로 끌어안아 숨기는 핵심 기법들을 한 페이지로 요약한다.
분할과 통합 기준 :: 언제 함수를 작게 쪼개고(Clean Code) 언제 깊은 모듈로 합칠지(Ousterhout) 나만의 판정 기준표를 정리한다.
추상화와 결합 기준 :: 좋은 추상화(정보 은닉)와 나쁜 추상화(성급한 일반화, 통과 계층)를 가르는 사례와 반례를 나란히 정리한다.
오류와 복원력 기준 :: 오류를 정의에서 없애는 법, 경계에서 거절하는 법, 그리고 분산·외부 연동에서 실패를 격리하는 원칙을 한 장으로 묶는다.
상태와 동시성 기준 :: 불변 데이터, 트랜잭션 경계, 강한 일관성과 결과적 일관성 중 무엇을 고를지 결정 트리를 정리한다.
거절 목록 :: 유명한 원칙이나 패턴이지만 맥락에 맞지 않아 거절했던 사례 다섯 가지와 그 판단 근거를 모은다.
ADR 모음 :: 지금까지 작성한 설계 노트 중 가장 대립이 뚜렷했던 다섯 편을 골라 표준 아키텍처 의사결정 기록(문제, 대안, 결정, 결과) 형식으로 다듬는다.
회고와 증거 :: 처음 설계를 볼 때와 지금의 기준이 어떻게 달라졌는지 적고, 각 원칙 옆에 직접 비교했던 사례 번호를 연결한다.
기록 한 페이지 :: 앞으로 새로운 시스템이나 모듈을 설계할 때 첫날 펼쳐 볼 '한 페이지 설계 원칙 핸드북'으로 전체를 압축한다.
소리 내어 읽기 :: 완성한 설계 핸드북과 ADR을 소리 내어 읽으며, 교조적인 문장이나 근거가 빠진 주장을 고친다.
기록 점검 :: 노트를 덮고 핵심 설계 원칙, 상반된 두 철학의 균형점, 그리고 대표 트레이드오프 사례를 백지에 다시 쓴다.

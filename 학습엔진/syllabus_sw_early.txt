한 이유 :: 한 커밋에는 한 이유의 변경만 넣는다. 화면 문구 수정과 검증 규칙 변경처럼 변경 이유가 다른 일을 한 단위에 섞지 않는다.

테스트 동반 :: 동작을 바꾸는 변경에는 그 동작을 검증하는 테스트를 함께 두어, 이 변경이 보장하는 계약이 무엇인지 드러낸다.
이름만 :: 이름만 바꾸는 리팩터링과 로직 수정을 분리해, 독자가 이름 변경과 동작 변경을 한눈에 구분할 수 있게 한다.
리뷰 크기 :: 변경을 잘게 쪼개 리뷰 속도를 높이는 관점과, 문맥이 끊기지 않게 한 흐름으로 묶는 관점을 파일 수와 읽기 시간으로 비교한다.

작업 메모 :: 착수 전에 구조 변경과 동작 변경의 순서를 먼저 스케치하고, 어느 쪽을 먼저 해야 변경 비용이 줄어드는지 비교한다.
단위 점검 :: 최근 변경이나 사례 연구의 커밋 이력을 보고, 이유별로 잘 나뉘었는지와 너무 잘게 쪼개 문맥이 깨진 곳은 없는지 점검한다.

늦게 합치기 :: 오래 갈라진 브랜치를 한꺼번에 합칠 때 발생하는 충돌 범위와 숨은 회귀 비용을 사례로 분석한다.

강제 푸시 :: 이력을 덮어써야 하는 예외적 상황과 그때 반드시 선행되어야 할 백업·합의 조건을 정리한다.

얕은 래퍼 :: 하는 일은 거의 없으면서 인터페이스와 설정만 복잡한 '얕은 모듈'을 찾아, 왜 이런 모듈이 전체 복잡도를 높이는지 분석한다.
호출자가 아는 것 :: 인터페이스를 쓰기 위해 내부 구현 파일까지 열어 봐야 한다면 추상화가 실패한 것임을 확인하고, 새어 나온 지식을 표시한다.
깊이 비교 :: 작은 클래스 여러 개로 쪼갠 설계와, 단순한 인터페이스 하나로 복잡한 일을 처리하는 깊은 모듈 설계를 나란히 비교한다.
통과 메서드 :: 인자를 그대로 하위 함수에 넘기기만 하는 통과 메서드(Pass-through Method)가 왜 계층 경계를 흐리는지 분석한다.
정보 누수 :: 내부 저장 형식이나 자료구조가 인터페이스 이름과 반환 타입에 그대로 드러나는 정보 누수(Information Leakage) 사례를 찾아 고친다.
모듈 경계 :: 함께 바뀌는 데이터와 그 데이터를 다루는 로직을 한 경계 안에 두어, 모듈 사이의 왕복 대화를 줄인다.
테스트는 경계 :: 내부 비공개 함수를 일일이 테스트할 때 생기는 리팩터링 취약성과, 공개 인터페이스 경계에서만 테스트할 때의 장단점을 비교한다.
깊은 쪽으로 :: 호출부마다 반복해서 처리하던 후처리나 예외 처리를 모듈 내부의 기본 동작으로 흡수해 인터페이스를 깊게 만든다.
호출 예 :: 좋은 인터페이스는 가장 흔한 사용 사례를 최소한의 인자와 설정으로 호출할 수 있게 해 준다는 기준을 코드로 확인한다.
깊이 기록 :: 모듈 하나를 골라 '밖으로 드러내는 약속'과 '안으로 숨긴 결정'을 두 칸 표로 정리한다.
깊이 점검 :: 얕은 모듈 하나를 합치거나 책임을 재배치해 인터페이스는 줄이고 내부 응집도는 높이는 설계를 완성한다.
작은 함수와 분할의 논쟁|79|91|깊이|분할|로버트 마틴(Clean Code)의 '극도로 작은 함수·단일 책임'과 아우스터하우트의 '지나친 분할 경계'를 정면으로 대조해 분할의 기준을 세운다.
짧은 함수 :: Clean Code처럼 함수를 몇 줄 단위로 잘게 쪼갰을 때 각 단계의 이름이 의도를 드러내는 장점을 먼저 확인한다.
이름 추출 :: 복잡한 식이나 조건에 이름을 붙여 함수로 빼냈을 때, 구현을 읽지 않고도 상위 흐름이 읽히는지 검증한다.
너무 잘게 :: 반대로 아우스터하우트의 비판처럼, 함수를 너무 잘게 쪼개 시선이 파일 곳곳으로 점프하고 문맥을 잃어버리는 부작용을 확인한다.
파일 수 :: 클래스를 잘게 나눈 뒤 기능 하나를 고칠 때 열어야 하는 파일 수와, 한 파일에 응집시켰을 때의 탐색 비용을 비교한다.
다음 변경 :: '단일 책임 원칙(SRP)'의 책임을 단순 동작 크기가 아니라 '변경의 이유(Actor)'로 해석할 때 분할 경계가 어떻게 달라지는지 본다.
점프 비용 :: 호출 계층이 깊어질수록 디버깅과 독해에서 발생하는 간접 참조 비용(Indirection Cost)을 직접 세어 본다.
한 함수로 :: 순서대로 한 번만 실행되는 조각 함수들을 다시 한 함수로 합쳤을 때 오히려 흐름과 지역 변수 관계가 더 명확해지는 사례를 분석한다.
추출 기준 :: '중복 제거'나 '독립된 개념'이 있을 때만 추출하고, 단순히 줄 수를 줄이기 위한 기계적 추출은 피하는 기준을 세운다.
중복과 추출 :: 우연히 모양만 비슷한 두 코드를 성급히 합쳤다가(잘못된 추상화), 나중에 요구사항이 갈라지며 플래그 인자가 붙는 문제를 다룬다.
테스트가 늘어남 :: 내부를 잘게 쪼갠 뒤 조각마다 모의 객체(Mock)를 붙여 테스트할 때 생기는 결합 비용을 분석한다.
읽기 순서 :: 위에서 아래로 신문 기사처럼 읽히는 배치(Stepdown Rule)와, 핵심 인터페이스를 먼저 두고 세부를 숨기는 배치를 비교한다.
나누기 기록 :: 같은 기능을 'Clean Code식 잘게 나눈 버전'과 'A Philosophy of Software Design식 깊게 묶은 버전'으로 나란히 적어 본다.
나누기 점검 :: 두 버전 중 현재 도메인의 변경 패턴에서 어느 쪽이 인지 부하와 수정 범위를 더 줄여 주는지 근거를 들어 선택한다.
같은 요구사항의 두 가지 설계|92|104|분할|비교|하나의 문제를 서로 다른 두 철학으로 각각 설계해 보고, 교조적 원칙 대신 맥락과 변경 비용으로 설계를 고르는 법을 익힌다.
같은 변경 :: 같은 요구사항을 놓고 A안(작은 객체와 다형성 중심)과 B안(단순한 데이터 구조와 깊은 모듈 중심) 두 가지로 설계한다.
얕은 버전 :: 역할마다 인터페이스와 클래스를 분리한 설계를 작성하고, 새로운 변형이 추가될 때와 기존 흐름을 읽을 때의 비용을 적는다.
깊은 버전 :: 세부 절차를 하나의 모듈 안에 감추고 외부에는 최소한의 진입점만 노출한 설계를 작성해 같은 기준으로 비용을 적는다.
파일 수 세기 :: 예상되는 다음 요구사항 세 가지를 두 설계에 각각 적용해 보고, 수정해야 하는 파일 수와 줄 수를 표로 비교한다.
어느 쪽이 쉬운지 :: 새로운 타입이 자주 추가되는 경우(개방-폐쇄 유리)와 새로운 연산이 자주 추가되는 경우(절차·데이터 중심 유리)를 구분한다(Expression Problem).
버린 버전 :: 선택하지 않은 설계가 무조건 틀린 것이 아니라, 어떤 가정이 바뀌면 다시 그 설계가 유리해지는지 조건을 적는다.
이유 문장 :: 설계를 선택한 이유를 '원칙 이름'이 아니라 '줄어든 인지 부하, 줄어든 수정 범위, 차단된 오류 가능성'으로 서술한다.
리뷰어에게 :: 동료에게 두 대안의 장단점과 최종 선택의 근거를 한 페이지로 설명하는 설계 비교문을 작성한다.
다음 버그 :: 두 설계 각각에서 가장 일어나기 쉬운 실수(예: 한쪽은 누락된 구현체, 다른 쪽은 거대해진 분기문)가 무엇인지 짚어낸다.
유지 비용 :: 지금 당장 짜기 쉬운 설계(전술적 프로그래밍)와 1년 뒤에도 고치기 쉬운 설계(전략적 프로그래밍)의 차이를 비교한다.
선택 기록 :: 최종 선택한 설계와 기각한 대안, 그리고 기각 사유를 짧은 아키텍처 결정 기록(ADR) 형식으로 남긴다.
재적용 :: 데이터 중심 설계와 객체 행위 중심 설계가 충돌하는 또 다른 사례를 골라 같은 비교표를 작성한다.
두 버전 점검 :: 언제든 한 가지 설계만 고집하지 않고, 최소 두 가지 대안을 만든 뒤 변경 비용으로 비교하는 절차를 백지에서 재현한다.
이름과 주석의 역할 분담|105|117|비교|이름|'주석은 실패를 만회하려는 수단이다(Clean Code)'라는 관점과 '주석은 코드가 담지 못하는 추상화와 의도를 완성한다(Ousterhout)'는 관점을 종합한다.
이름 먼저 :: 주석을 달기 전에 변수·함수·타입의 이름만으로 의도와 단위를 드러낼 수 있는지 먼저 고쳐 본다.
주석을 지움 :: 코드를 그대로 한국어나 영어로 다시 읽어 줄 뿐인 중복 주석(예: `i를 1 증가시킨다`)은 오히려 시선을 방해하므로 지운다.
인터페이스 주석 :: 반대로 시그니처만으로는 알 수 없는 전제조건, 경계값, 부작용, 반환값의 의미는 인터페이스 주석으로 명확히 남긴다.
서명만으로 :: 구현 코드를 가리고 함수 서명과 인터페이스 주석만 읽었을 때 호출자가 망설임 없이 쓸 수 있는지 점검한다.
오해 한 줄 :: 이름은 간결하지만 호출자가 잘못된 가정을 하기 쉬운 자리(예: 닫는 책임이 누구에게 있는지, 스레드 안전한지)를 주석으로 방어한다.
구현 주석 :: 복잡한 알고리즘이나 성능 우회 코드 안에서는 '무엇을 하는지'가 아니라 '왜 평범한 방법을 쓰지 않았는지'를 주석으로 남긴다.
주석이 거짓말 :: 코드는 바뀌었는데 주석은 옛날 말을 하고 있는 사례를 찾아, 주석을 코드 가까이 두거나 테스트·타입으로 대체하는 법을 배운다.
이름 길이 :: 좁은 범위의 지역 변수는 짧아도 되지만, 넓은 범위에서 쓰이는 인터페이스 이름은 역할과 단위를 분명히 담아야 하는 이유를 비교한다.
둘 다 남김 :: 코드로 표현할 수 있는 것은 코드로 옮기고, 코드로 표현할 수 없는 설계 의도·추상화·제약만 주석으로 남기는 기준을 세운다.
호출 예제 :: 복잡한 모듈의 사용법은 긴 설명문보다 실행 가능한 짧은 예제 코드나 테스트가 더 정확하게 전달함을 확인한다.
지운 이유 :: 불필요한 주석을 지운 자리와, 꼭 필요해서 새로 작성한 인터페이스 주석 자리를 나란히 두고 차이를 설명한다.
남긴 이유 :: 좋은 주석은 코드를 읽기 전에 고수준의 직관을 주고, 나쁜 주석은 낮은 수준의 코드를 반복한다는 기준을 정리한다.
주석 점검 :: 모듈 하나를 골라 중복 주석은 걷어내고, 호출자를 위한 계약 주석과 설계 이유 주석만 남기는 리팩터링을 수행한다.
오류를 정의에서 지우기 vs 경계에서 드러내기|118|130|이름|오류|예외를 촘촘히 던지고 처리하라는 관점과, 인터페이스 정의를 바꿔 예외 상황 자체를 없애라는(Define Errors Out of Existence) 관점을 비교한다.
오류를 없앰 :: 아우스터하우트의 제안처럼, 예외를 던지는 대신 정상 동작의 정의를 넓혀 호출자가 오류 처리를 신경 쓰지 않게 만드는 설계를 연습한다.
특수 경우 :: null이나 빈 값 때문에 곳곳에 if문이 생길 때, 특수 객체(Null Object)나 빈 컬렉션 반환으로 분기를 없애는 기법을 적용한다.
한 종류로 :: 반대로, 묻어 두면 데이터가 오염되는 치명적 오류는 절대 삼키지 않고 즉시 실패(Fail-Fast)시켜야 하는 이유를 대조한다.
호출자에게 :: 호출자가 복구할 수 있는 오류(재시도, 입력 수정)와 복구할 수 없는 오류를 구분해 인터페이스에 드러낼 것만 남긴다.
로그와 실패 :: 예외를 잡아서 로그만 찍고 정상인 것처럼 진행하는 코드가 왜 더 큰 장애를 만드는지 분석한다.
무시된 오류 :: 에러 코드나 반환값을 무시할 수 있는 인터페이스와, 타입(Result/Option)이나 예외로 처리를 강제하는 인터페이스를 비교한다.
재시도 :: 일시적 네트워크 오류처럼 재시도가 의미 있는 경우와, 멱등성(Idempotency)이 없어 재시도하면 중복 실행이 되는 경우를 구분한다.
경계 검사 :: 시스템 가장자리(외부 입력, API 경계)에서는 엄격하게 검증해 거절하고, 내부 핵심 로직에서는 검증된 타입을 믿고 단순하게 짜는 구조(Parse, Don't Validate)를 익힌다.
내부 단정 :: 절대 깨지면 안 되는 내부 불변식(Invariant)은 단정문(Assert)으로 확인하고, 사용자 입력 오류와 섞지 않는다.
메시지 :: 오류가 났을 때 내부 변수명만 찍는 대신, 무엇이 잘못되었고 호출자나 운영자가 무엇을 해야 하는지 담는 기준을 세운다.
테스트로 실패 :: 예외를 없애 단순해진 경로와, 경계에서 정확히 거절해야 하는 경로를 각각 테스트로 검증한다.
정의에서 제거 :: 기존 모듈에서 불필요한 예외나 특수 분기를 정의 변경으로 흡수했을 때 호출부 코드가 얼마나 줄어드는지 확인한다.
오류 점검 :: 어떤 오류는 정의를 바꿔 없애고, 어떤 오류는 경계에서 즉시 거절해야 하는지 두 기준을 사례로 대조해 정리한다.
설계 리뷰와 근거 있는 비평|131|143|오류|리뷰|취향이나 권위에 기대는 리뷰를 넘어, 변경 비용·정보 은닉·결합도라는 객관적 기준으로 설계를 비평하고 토론하는 법을 익힌다.
리뷰 질문 :: '내 스타일대로 고치세요'라고 말하기 전에, '이 설계가 어떤 결정을 숨기고 어떤 변경을 쉽게 만드는가'를 먼저 묻는다.
원칙 인용 :: 같은 코드를 Clean Code 관점(작은 단위, 명시적 역할 분리)과 A Philosophy of Software Design 관점(깊은 모듈, 정보 은닉)에서 각각 비평해 본다.
반대 원칙 :: 두 원칙이 충돌할 때 어느 한 책의 문장을 교리처럼 쓰지 않고, 앞으로 가장 자주 일어날 변경에서 어느 쪽이 유리한지 따진다.
예로 말하기 :: 추상적인 인상 비평 대신, 구체적인 변경 시나리오나 깨지는 입력 예를 들어 설계의 약점을 짚는다.
칭찬과 결함 :: 복잡도를 잘 숨긴 좋은 설계 결정과, 결합도를 높인 위험한 결정을 함께 짚어 균형 잡힌 리뷰를 작성한다.
크기 제한 :: 아키텍처의 큰 방향에 대한 피드백과 지역적인 변수명·포맷 피드백을 구분해, 핵심 설계 논의가 사소한 지적에 묻히지 않게 한다.
작성자 응답 :: 리뷰 의견에 답할 때도 방어적 태도 대신, 당시 고려한 트레이드오프와 제약 조건을 근거로 설명한다.
고친 뒤 :: 리뷰를 통해 발견한 더 나은 추상화나 단순화 방법을 코드와 설계 노트에 반영한다.
대화 기록 :: 의견이 갈렸던 지점과 최종 합의한 기준을 기록해 두어, 다음번에 같은 논쟁을 처음부터 반복하지 않게 한다.
막힌 리뷰 :: 두 설계 대안 중 당장 우열을 가리기 어려울 때, 어떤 관찰 지표나 실험으로 결정을 내릴지 합의하는 법을 배운다.
결정 남기기 :: 왜 A 방식 대신 B 방식을 택했는지 핵심 근거를 한 문단으로 남겨 미래의 유지보수자에게 전달한다.
다시 읽기 :: 시간이 지난 뒤 자신이 짰던 설계를 제3자의 눈으로 다시 리뷰하며, 당시 보지 못했던 결합도와 누수를 찾아낸다.
리뷰 점검 :: 설계 사례 하나를 골라 양쪽 관점의 비평과 절충안을 포함한 한 페이지 설계 리뷰를 작성한다.
원칙의 한계와 의도적 거절|144|156|리뷰|거절|모든 설계 원칙(DRY, SOLID, 작은 함수, 디자인 패턴)에는 적용 한계가 있음을 이해하고, 근거를 가지고 원칙을 거절하는 판단력을 기른다.
거절 문장 :: 유명 교재나 업계에서 흔히 권하는 규칙 중, 현재 문제 맥락에서는 오히려 독이 되는 규칙 하나를 명시적으로 지목한다.
어떤 책 :: 그 규칙이 Clean Code, A Philosophy of Software Design, GoF 패턴 등 어디에서 비롯되었는지와 원래 해결하려던 문제가 무엇인지 적는다.
결과로 거절 :: 그 규칙을 기계적으로 적용했을 때 발생하는 부작용(클래스 폭발, 과도한 간접 계층, 성급한 추상화)을 구체적으로 보여 준다.
파일 수 근거 :: 원칙을 그대로 따랐을 때와 의도적으로 거절하고 단순하게 짰을 때의 구조 복잡도를 나란히 비교한다.
버그 근거 :: 과도한 분리나 추상화 때문에 전체 제어 흐름을 놓쳐 생기는 버그 사례를 분석한다.
읽기 근거 :: 반대로 원칙을 거절해 한곳에 모아 두었을 때 코드가 너무 길어지거나 다른 책임이 섞이지는 않는지 반대 위험도 점검한다.
임시 수용 :: 지금은 요구사항이 단순해 단순한 구조(예: 조건문 하나, 약간의 중복)를 택하되, 언제 추상화로 전환할지 기준선(Rule of Three 등)을 정한다.
다시 볼 날 :: '세 번째 변형이 추가될 때'나 '두 팀이 각각 수정하기 시작할 때'처럼 설계를 다시 쪼갤 구체적인 신호(Trigger)를 적어 둔다.
팀 규칙과 다름 :: 일반적인 관례와 다른 선택을 했을 때는 나중에 읽는 사람이 실수로 오해하지 않도록 그 이유를 코드 근처에 분명히 남긴다.
문서에 남김 :: '따른 원칙, 거절한 원칙, 거절한 근거, 다시 검토할 조건'의 네 줄로 설계 판단을 기록한다.
코드에 남김 :: 성급한 추상화(Wrong Abstraction)에 빠진 코드를 다시 풀어서(Inline) 단순한 중복으로 되돌린 뒤 올바른 경계를 다시 찾는 연습을 한다.
한 달 뒤 :: 과거에 내렸던 설계 결정을 다시 펼쳐 보고, 그때 예상했던 변경과 실제로 일어난 변경이 맞았는지 복기한다.
거절 점검 :: 서로 상반되는 두 원칙 중 하나를 택하고 다른 하나를 거절하는 판단문을 실제 설계 사례에 대해 작성한다.
